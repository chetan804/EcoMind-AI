# Database schema overview

PostgreSQL is the only authoritative store. The schema is defined by SQLAlchemy models **inside the module that owns each table** and evolved only through Alembic migrations (`backend/migrations/versions`). Column-level detail is in the generated [data-dictionary.md](data-dictionary.md); the relationships are drawn in the generated [er-diagram.md](er-diagram.md).

## Conventions
- Table names: plural snake_case. Primary key `id UUID DEFAULT gen_random_uuid()` (join tables use composite keys).
- `created_at`/`updated_at` `timestamptz` on mutable tables; append-only tables (status history, events, ledger, audit, custody) have `created_at` only and are never updated. The database enforces it with triggers on `custody_events`, `reward_ledger_entries` (0007), `vehicle_location_events` (0011), `audit_logs` and `collection_task_status_history` (0017); the one permitted change is detaching a removed user from `audit_logs.actor_id`. TRUNCATE is not covered by row triggers: the application role should not hold that privilege.
- Naming convention for constraints/indexes is fixed in `app/db/base.py` (`pk_`, `fk_`, `uq_`, `ix_`, `ck_`), so autogenerated migrations are stable.
- Enumerations: `VARCHAR` + `CHECK` named `ck_<table>_<column>_valid`; values live in each module's `constants.py`.
- Quantities: unit in the column name (`*_kg`, `*_km`, `*_min`) or an explicit `unit` column (forecasts, anomalies: `kg|t|m3|l|item`). Never unit-less numbers.
- Location: nullable `latitude`/`longitude numeric(9,6)` pairs with range checks and both-or-neither check.
- Foreign keys default to `ON DELETE RESTRICT`; cascades only for pure children (sessions, stops, status history, events, notifications). Users with history are deactivated (`is_active`), not deleted.
- Every foreign key column is indexed (verified by `test_migrations.py`).
- Polymorphic references (`reward_ledger_entries.source_id`, `notifications.entity_id`, `audit_logs.entity_id`) have no FK by design.

## Key relationships
```
users ─┬─< waste_reports ─< media_assets ─< classification_predictions >─ classification_model_versions
       │                                           └──> material_categories <── sorting_guidance
       ├─< collection_tasks ─┬─< collection_assignments >── fleet_vehicles ── facilities
       │        │            ├─< collection_task_status_history
       │        │            └─< collection_events
       │        └─< route_stops >─ route_plans (vehicle, driver, start/end facility)
       ├─< recovery_records (facility, material_category, task?, evidence media?) ─< material_passports ─< custody_events
       ├─< community_incidents      ├─< reward_ledger_entries (self-reference for reversals)
       ├─< notifications            └─< audit_logs (actor, SET NULL)
facilities, material_categories ─< forecast_results, anomaly_alerts (optional scope)
```

## Invariants enforced by the database
Unique case-insensitive email; one active assignment per collection task (partial unique index); route stop targets exactly one of task/facility and has a unique sequence per route; recovered weight ≤ input weight and verification fields consistent with status; prediction confidences in [0,1], review fields consistent with review status, one prediction per (media, model version); idempotent `earned` ledger entries per (user, source); non-zero points, reversal rows reference an entry; forecast period/interval ordering; anomaly alerts require an explanation; geographic ranges; positive capacities and weights. Tests: `backend/tests/integration/test_schema_constraints.py`.

## Deliberate omissions
- **Sensor devices/readings:** not created. No hardware exists and no requirement is accepted. They will be added through a migration owned by `integrations/sensors` or a dedicated module when required.
- **Model version table for forecasting/anomaly detection:** those tables store `model_name`/`model_version` strings, because baseline models have no artifacts and `classification` should not be a dependency of unrelated modules.
- **Seed data (roles, permissions, material categories):** seeded by data migrations in the milestone that defines them (roles and permissions in `0002` and later migrations; material categories in `0006`; the support articles by the `seed-support-knowledge` CLI command), never invented at run time.
- **Facility accepted materials, pickup schedules, organizations:** not modelled until required.

## Evolving the schema
See `docs/operations/runbook.md` ("Database migrations"): autogenerate, review by hand, add constraint tests, regenerate the data dictionary, never edit an applied migration, never reset a database to make a migration pass.
